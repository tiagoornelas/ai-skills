# Design It Twice

Ensures that no high-consequence design decision is locked in based on the first idea. The foundational theory is in [references/design-it-twice.md](references/design-it-twice.md); this skill is the operational procedure.

---

## 1. Core Principle

This skill **does not replace** the software architect. It invokes the architect **once per alternative**, in isolated contexts, and orchestrates the structured comparison. All design analysis for each alternative derives from [`software-designing`](../software-designing/SKILL.md) and its analytical lenses.

---

## 2. When to Use and at What Scale

| Scenario | Execution Mode |
| :--- | :--- |
| Minor decision (single function/class signature, localized contract) | **Inline**: draft alternatives in the current context, strictly at the interface level. |
| Major decision (system decomposition, public API, core mechanism, service boundaries) | **Isolated subagents**: one execution of `software-designing` per alternative (Section 4). |
| Trivial or easily reversible decision | Skip. Record the choice directly. |

Isolation matters: an agent that has already drafted Alternative A tends to anchor on it and produce minor variations of A. Completely isolated contexts, each constrained to follow a distinct architectural axis, produce genuinely divergent designs.

---

## 3. Workflow

### Step 1: Frame the Problem Once
Execute Steps 1 and 2 of [`software-designing`](../software-designing/SKILL.md) (frame the problem and diagnose complexity) **exactly once**, consolidating the findings into a unified **Context Packet**:
- the core problem, consumers, and constraints, verbatim (*ipsis litteris*) as received from the human or caller agent;
- relevant existing code and architecture, if applicable;
- the **decision to be made**, phrased as a clear question (e.g., "What should be the interface of the text storage module?");
- the primary comparison criterion (by default: ergonomics and ease of use for consuming callers).

Open questions that only the human can answer must be resolved **before** generating alternatives; otherwise, each alternative will invent contradictory assumptions.

### Step 2: Establish Radically Different Axes
Before drafting code or diagrams, define **2 to 4 distinct design axes**, each governed by a fundamentally different architectural premise. Examples of axes that reliably produce divergent alternatives:
- **Unit of Abstraction**: by-line vs. by-character vs. by-range; by-record vs. by-batch vs. stream-based.
- **Locus of Knowledge**: centralized in a deep module vs. distributed among peers vs. delegated to platform primitives.
- **Interaction Model**: synchronous request/reply vs. event-driven pub/sub vs. asynchronous batch queue; push vs. pull.
- **State Model**: encapsulated mutable state vs. immutable data transformations vs. append-only event log.
- **Boundary Placement**: unified deep module vs. layered general/specialized separation vs. decoupled service.

Discard axes that merely rename the same underlying decomposition.

### Step 3: Generate Each Alternative in Isolation
For each axis, invoke `software-designing` with the delegation brief in Section 4. Each execution produces **one fully realized alternative**, explored seriously on its own merits without premature cross-comparison.

### Step 4: Compare
Construct the comparison matrix (Section 5) using the criteria from [references/design-it-twice.md](references/design-it-twice.md) (Section 3). For each alternative, enumerate candid pros and cons using architectural concepts: depth, information leakage, generality, abstraction layers, complexity placement, failure modes, and obviousness.

### Step 5: Choose, Combine, or Redesign
- **One clearly dominates** → recommend it.
- **Alternatives offer complementary strengths** → formulate a **hybrid combination**, explicitly tracing which strength originates from which alternative. The hybrid must pass through `software-designing` lenses to ensure conceptual cohesion.
- **None are compelling** → use discovered weaknesses to formulate a fresh design axis and return to Step 3 (maximum one additional round; if still unresolved, escalate to the human as an ill-defined problem).

### Step 6: Present via the Human Layer
Present a module map per alternative (side-by-side using [`visualize-it`](../visualize-it/SKILL.md)) alongside the comparison matrix. Selecting between alternatives that impact contracts, boundaries, or dependency direction is a **human decision**: state the agent recommendation and solicit a decision. In agent-to-agent delegation, mark it as pending.

Once decided, the winning design proceeds through Step 6 of `software-designing` (decision record and handoff to [`coding`](../coding/SKILL.md)). Document rejected alternatives and rejection rationales in the decision record.

## 4. Subagent Delegation

Follow [subagent-delegation.md](../ai-assisted-software-development/references/subagent-delegation.md): self-contained brief with absolute skill paths. Harness tooling:
- **Claude Code**: `Agent` tool with `general-purpose` type, one call per alternative, **all launched in the same message turn** to run concurrently.
- **Antigravity CLI**: `invoke_subagent` with `TypeName: "self"`.
- **Codex**: one isolated subprocess or thread per alternative.

Subagent brief template (populate and pass Context Packet verbatim):

```markdown
Follow the `software-designing` skill (<skills>/software-designing/SKILL.md) in
"invoked by another agent" mode.

## Context Packet
<Complete Context Packet, verbatim>

## Your Mandatory Design Axis
<Axis name + core architectural premise>. Design the BEST possible solution that
adheres strictly to this premise. Do not propose alternatives outside this axis
and do not dilute it: peer agents are covering the other axes.

## Deliverable
A Design Brief containing ONE alternative (omit the "Alternatives Considered" table).
Must include: module map, interface cards, failure modes, and a "Known Weaknesses"
section listing honest limitations of this approach.
Cost strictly in relative terms (complexity, risk, change footprint), with zero
schedule estimates or project delivery phases.
Do not write implementation code.
```

## 5. Output Format

```markdown
## Decision at Hand
<The design question, in one sentence>

## Alternatives
### A — <Axis Name>
<Core concept in 2–3 sentences + module map + primary interface>
### B — <Axis Name>
...

## Comparison Matrix
| Criterion | A | B | C |
| :--- | :--- | :--- | :--- |
| Ease of use for callers (primary criterion) | | | |
| Interface simplicity / module depth | | | |
| Generality | | | |
| Information leakage | | | |
| Exposed failure modes | | | |
| Implementation efficiency / relative cost (no schedules) | | | |
| Ergonomics for likely future changes | | | |

## Recommendation
<selection | hybrid combination (tracing traits to source alternatives) | redesign>
<justification grounded in reference concepts>

## Pending Decision (Human Layer)
<options, recommendation, and cost of error>
```

---

## 6. Success Validation

- [ ] At least **two alternatives** were evaluated, each derived from a **fundamentally different premise** (not trivial syntactic or naming variations).
- [ ] No strawman alternatives: each represents the strongest possible realization of its axis and lists candid weaknesses.
- [ ] All alternatives originated from the **exact same Context Packet**, passed without loss of context.
- [ ] The matrix evaluates all alternatives across identical criteria, prioritizing caller ergonomics.
- [ ] The recommendation explicitly declares a choice, hybrid combination, or redesign, and any hybrid was re-verified against design lenses.
- [ ] The final decision was made by the human (or flagged as pending in agent mode), with rejected alternatives recorded alongside rationale.
